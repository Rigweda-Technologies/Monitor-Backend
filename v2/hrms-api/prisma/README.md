# HRMS v2 PostgreSQL clients

HRMS v2 owns one lifecycle-managed Prisma client per PostgreSQL database: `monitor` and `payroll`. MongoDB remains Mongoose-backed. The clients use Prisma 7.10.1's PostgreSQL adapter and independently bounded pools. `npm run prisma:generate` generates both client outputs under the ignored `generated/` directory; `npm run prisma:validate` validates schemas without connecting to a database.

The monitor schema maps the existing physical tables from `desktop/backend/src/database/schema.js`, including HRMS-owned `monitor_device_health` and the extended Cloudinary settings columns. Names use `@map`/`@@map`; generation and validation do not create tables or indexes. The monitor service and HRMS V1 remain the current physical schema owners. V2 startup does not replay DDL or migrations.

The payroll Prisma schema currently supplies a raw-query client only. The canonical table and column definitions remain the 11 existing JavaScript migrations in `hrms/back-end/src/payroll/migrations/`; no schema was introspected from a hosted database. Every v2 payroll query must use Prisma's parameterized raw-query API against that unchanged physical schema. Before claiming payroll parity, the migration inventory must be mapped and tested against an isolated representative copy, including DATE, NUMERIC, UUID, JSONB, constraints and tenant ownership. This file does not authorize `db push`, migration replay, schema reset or production access.

Configuration uses `MONITOR_DATABASE_URL` (or the legacy `MONITOR_TOOL_DATABASE_URL` / `DESKTOP_MONITOR_DATABASE_URL` aliases) and the existing payroll settings (`PAYROLL_DATABASE_URL` or `PGHOST`/`PGDATABASE`/`PGUSER`/`PGPASSWORD`, gated by `PAYROLL_DB_ENABLED`). Credentials must be supplied outside committed files. `PAYROLL_DB_ENABLED=true` without a valid URL fails configuration. Tests that write PostgreSQL data must use explicitly isolated database names and be reported separately when skipped.
