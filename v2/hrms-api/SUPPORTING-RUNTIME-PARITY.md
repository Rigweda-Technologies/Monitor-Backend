# HRMS supporting runtime parity

This note compares supporting behavior found in `hrms/back-end` with the independent HRMS v2 service. It records source behavior and discovered launch paths; it does not authorize v2 startup, job ownership, or client cutover.

## Realtime events

V1 creates a Socket.IO server on the HTTP server at `SOCKET_IO_PATH` or `/api/socket.io`. It applies the configured CORS allowlist and optionally a Redis Socket.IO adapter. Handshakes accept `auth.token` or the Authorization header. V1 verifies the JWT, loads the user, requires an active account and a matching active token-list entry, joins `attendance:<organizationId>:<userId>` and `monitor-settings:<organizationId>`, and disconnects when the token expires. It emits:

| Event | Room |
|---|---|
| `attendance:updated` | User attendance room |
| `notification:new` | User attendance room |
| `monitor-settings:updated` | Organization monitor-settings room |

V2 has no Socket.IO server, Socket.IO dependency, or Redis adapter setup. `integrations/realtime.js` is composed by `runtime.js` around an externally owned Socket.IO instance supplied as `socketServer`; it is disabled by default, creates no server, and does not configure CORS or Redis. When explicitly enabled, it uses the v2 session authenticator, joins the same rooms, preserves event names, and enforces expiry using verified token claims. The caller must configure the v1 path/origins and own adapter/server shutdown. Attendance, notification, and monitor-settings changes call this bridge; with the default disabled adapter they emit nothing.

## Push notifications

V1 mounts FCM token routes under `/api/v1/notifications`, stores tokens on the user, and removes a matching token from other users before registration. Notification creation starts best-effort asynchronous delivery; missing recipients, tokens, or Firebase configuration skip delivery. Invalid/unregistered tokens are removed. Firebase accepts service-account JSON or the project/email/private-key environment values.

V2 already defines the same two token operations in its notification module, adds the `pushTokens` schema path when composing notification models, globally moves tokens on registration, removes invalid tokens, and sends best-effort pushes from notification creation through `createFirebasePushSender`. The v2 sender has a bounded provider timeout. Its runtime does not create a second push worker. Delivery can occur when Firebase credentials are configured, so callers must avoid creating the same notification through both versions during a cutover window.

## Bootstrap and maintenance commands

V1's `bootstrap.system.js` calls `ensureSystemBootstrap`, which creates the SYSTEM organization, wildcard permission, superadmin role, user and organization membership. Its source also contains a fixed default password and prints that password when the script runs. V2 provides `npm run bootstrap:system` as an explicit operator command requiring a supplied email and password; it refuses to grant SYSTEM membership to an unrelated existing account and prints no credentials. It does not run at server startup. V1 role seeding runs at startup and is also exposed as a manual script. V2 seeds roles during organization creation and provides `npm run seed:organization-roles` for existing non-SYSTEM organizations; it defaults to a read-only count and requires `--apply` for writes. The V1 hard-delete script inventory and JSON report are available through `npm run org:hard-delete`, with execution delegated to the V2 lifecycle service. Other V1 scripts are one-time data repairs, schema migration runners, or destructive maintenance operations; they are not part of normal API/runtime behavior and must be evaluated individually before any V2 equivalent is run against shared data.

## Queues, workers, and cron source

V1 BullMQ uses `JOB_QUEUE_NAME` or `rigweda-system-jobs`. `jobs:scheduler` registers repeat jobs for leave credit, leave carry-forward, probation completion, and organization-document expiry. Defaults are midnight daily except document expiry at 08:30. The HTTP process starts that scheduler only when `ENABLE_JOB_SCHEDULER=true`. `jobs:worker` is a separate process, connects MongoDB, defaults to concurrency 1, and processes those four jobs plus payroll-run compute. The worker has completion/failure logs; the source does not add a shutdown/signal handler here.

V1 also contains module-scope `node-cron` files for attendance auto-checkout at 23:59 and daily leave credit, carry-forward, and probation notifications. Repository source search found no imports of those files and no package script that directly starts them. Their deployment launch state is therefore unknown. If an operator loads them alongside the BullMQ worker, leave credit, carry-forward, and probation work can run through two scheduling paths. Attendance auto-checkout updates attendance and timesheet hours at the machine's local end-of-day boundary.

V2 does not start a scheduler, worker, node-cron task, or queue connection. `src/jobs/runtime.js` provides injected scheduler/worker adapters with explicit `enabled` flags (default false), start/close hooks, v1 job names, and default cron patterns. `runtime.js` composes the handlers and adapters; callers may inject `jobQueue`, `jobWorkerFactory`, `jobConnection`, and loaded `JOB_QUEUE_NAME`, `JOB_CRON_*`, and `JOB_WORKER_CONCURRENCY` settings. Operators must explicitly start the returned scheduler/worker; the v2 HTTP server does not start them.

V2 also exposes the V1 node-cron attendance auto-checkout behavior as the optional `attendance-auto-checkout` job at `59 23 * * *`. It closes open attendance records for the local day and upserts that date's weekly timesheet hours. `JOB_TIMEZONE` controls the repeat schedule timezone and defaults to the host's resolved timezone. It preserves V1's write order: attendance is saved before timesheet hours are upserted. Therefore a timesheet failure leaves the attendance closed and a later run does not retry its timesheet update, matching the current V1 failure behavior. This job was not part of V1's BullMQ scheduler, and the source cron file has no known importer, so operators must verify whether that V1 cron is running and assign exactly one owner before enabling V2 scheduling.

V2 payroll compute can enqueue only when a queue is injected; without one, async compute returns an unavailable error. `src/jobs/business-handlers.js` provides injected processors for leave credit, leave carry-forward, probation completion notification, organization-document expiry notification and attendance auto-checkout. `runtime.js` composes these with the payroll compute processor into its optional worker adapter. Document expiry delegates to the v2 document service, which retains the 24-hour per-recipient/document deduplication check and now uses `NotificationService.createNotificationSafe`, including configured FCM and enabled realtime delivery.

V2 carry-forward writes a `carryForwardedFromCycleYears` marker on each target leave balance and atomically guards the increment with that marker. This is an additive field on the existing collection, excluded from ordinary Mongoose projections with `select:false`, and does not create an index or collection. The field survives retries, including a retry after the target was created or updated. It does not make concurrently running workers safe across an old v1 worker: v1's strict Mongoose schema may omit the marker if it saves that balance, so only one version should own these jobs during a cutover. Probation retries look up an already persisted `probation_completed` notification by organization, recipient, employee, and probation end date before sending it again. This prevents ordinary retry duplication after persistence, but simultaneous workers can both pass the lookup before either inserts; run one worker or add an approved atomic claim/dedupe mechanism before enabling concurrency. Leave-credit writes are guarded by `lastCreditedAt` and are retry-safe only when the existing unique leave-balance index is present. That index is declared in the v2 model with automatic index creation disabled, so it must already exist in MongoDB. These recurring jobs remain disabled until one version owns the schedule.

The scheduler and worker adapters preserve names and dispatch but do not create a broker connection. The external caller must supply the existing queue/worker implementations and ensure one version owns each schedule during coexistence. No v2 worker or scheduler is auto-started.

## Startup, bootstrap, and readiness

V1 startup connects MongoDB and payroll PostgreSQL, initializes Socket.IO, runs `ensureSystemBootstrap`, then attempts to seed roles and permissions for every non-SYSTEM organization. Scheduler startup is optional as described above. `/ready` checks MongoDB, enabled Redis, and enabled payroll PostgreSQL.

V2 startup builds its independent Fastify runtime, connects its configured MongoDB/Prisma clients, listens, and closes those resources on SIGTERM/SIGINT. It does not load v1 environment files, create a SYSTEM user, seed organization roles at startup, create a Socket.IO server, or start background work. Organization role seeding occurs through its organization-creation service or the explicit dry-run-first `seed:organization-roles` CLI. V2 `/api/v2/ready` checks MongoDB and the opt-in payroll Prisma connection; it does not establish monitor PostgreSQL, Redis, Firebase, socket, or worker health.

## V1 maintenance commands and V2 gaps

The v1 package exposes explicit scripts for attendance deduplication; organization residual cleanup and hard delete; attendance date and rotational week-off migrations; organization-document migration; payroll migration/status, tenant seeding, and data clearing; SYSTEM bootstrap; and role seeding. These are operator-invoked tools, not startup behavior. Some perform destructive database or index operations and require their own approved isolated/production process. V2 now has explicit SYSTEM bootstrap, role-seeding, and organization hard-delete tools, but no equivalent general maintenance-script set. Its Prisma client generation and payroll legacy utilities do not reproduce one-time schema/data repair workflows.

## Current V2 adapter tests

`tests/realtime-adapter.test.js` covers the opt-in default, session-authenticated handshake, scoped rooms, v1 event names, and rejected missing/expired sessions. `tests/jobs-runtime-adapter.test.js` covers disabled-by-default scheduler/worker behavior, preserved job names/default schedules, timezone injection and handler dispatch. `tests/job-business-handlers.test.js` covers leave-credit period guards, leave-type/employee selection, carry-forward caps and retry behavior, probation recipient selection/self-exclusion/notification deduplication, attendance auto-checkout and recovery after a failed hours upsert, and the document-service delegation. `tests/attendance-auto-checkout-v1-parity.test.js` and `tests/business-jobs-v1-parity.test.js` compare these four migrated job behaviors directly with V1 services. Organization-document persistence tests cover the 24-hour deduplication rule and injected notification delivery. These tests do not verify a live queue, Redis, network Socket.IO server, CORS, Redis fan-out, browser/client behavior, or external delivery.
